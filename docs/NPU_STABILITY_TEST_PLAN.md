# NPU 서버 안정성 테스트 계획

> 목적: "요즘 서버가 자주 죽는다"는 증상을 재현·격리한다.

## -1. 근본 원인 확정 + 수정 완료 (2026-08-02)

사용자 확인: *"remembr eval 하다가 서버가 잘 안 돌아가서 Ctrl-C 해서 30분 기다렸는데도 서버가 안
내려갔어."* 이 한 문장으로 아래 일반 스트레스 계획보다 먼저 원인을 특정할 수 있었다.

**원인**: `uvicorn.run()`의 `timeout_graceful_shutdown` 기본값이 `None` → SIGINT를 받아도 진행 중인
HTTP 요청이 끝날 때까지 **무한 대기**. `remembr+` 에이전트 질문은 평균 70~100초 걸리는데, 그 사이
Ctrl-C가 오면 uvicorn이 응답을 기다리며 멈춘다. 서버의 안전 종료 로직(`worker.join(180)`으로 device를
깨끗이 닫는 코드)은 이미 올바르게 있었지만 `uvicorn.run()`이 리턴해야 실행되므로, **그 지점에 영원히
도달 못 하고 있었다.** 30분 뒤 사용자가 결국 강제 종료했을 가능성이 높고, 연산 중이었다면 그게 바로
이 세션에서 반복된 보드 wedge(force-kill 중 device teardown 스킵)로 이어졌을 것.

**수정**: `tt_server/tt_infer_server.py`에 `timeout_graceful_shutdown=5`(초, `TT_SHUTDOWN_TIMEOUT`으로
조정 가능) 추가. 워커의 안전 종료(진행 중 작업은 끝까지 실행 후 정리)는 그대로 보존됨.

**실측**: 8B 캡션(약 40초) 요청 중 SIGINT → 30분+ 무응답이던 것이 **38초 만에 정상 종료**로 개선.
클라이언트는 11.7초 후 명확한 500 에러 수신(무한 행 아님). 종료 후 보드 독립 테스트로 생존 확인.
자세한 내용은 `docs/DEV_STATUS.md` 2026-08-02(2) 항목 참고.

**이 발견의 의미**: 아래 티어별 스트레스 계획은 여전히 유효하지만, 우선순위가 낮아졌다 — "자주
죽는다"의 가장 유력한 설명(eval 중 Ctrl-C가 안 먹혀서 결국 강제 종료)은 이미 원인 특정 + 수정 +
실측 검증까지 끝났다. 아래 T1~T6은 **이 수정 이후에도 남아있을 수 있는 다른 원인**을 찾기 위한
후속 검증으로 격을 낮춰 진행한다.

## 0. 사전 확인 (실행 완료, 결과가 계획의 근거)

실행 전 현재 서버가 **이미 알려진 두 사망 원인**을 다시 밟고 있는지부터 확인했다 — 아니면 계획을 처음부터 잘못 세우는 것이므로.

| 확인 항목 | 결과 |
|---|---|
| `TT_METAL_INSPECTOR` | `0` (꺼짐) — YAML flush 누적으로 인한 slowdown 아님 |
| 빌드 | `build_Release` (Tracy 아님) — zone 누적으로 인한 RSS 무한증가 아님 |
| 현재 RSS | 3.3GB, 가동 59분, 정상 범위 |
| 최근 서버 로그 | 크래시 흔적 0건 (이번 재기동 이후) |
| 시스템 메모리/디스크 | 여유 충분 (가용 50GB / 디스크 278GB) |

→ **알려진 원인 2가지는 배제됨.** "자주 죽는다"는 이 세션 로그 밖의 관찰이거나, **아직 스트레스 테스트한 적 없는 패턴**에서 온 것으로 보고 계획을 짠다.

## 1. 이미 확정된 사실 (테스트 설계의 기준)

같은 것을 다시 발견하려고 위험을 반복하지 않기 위해, 이번 세션에서 이미 실측된 것들:

**안전하다고 검증됨:**
- in-process `close_mesh_device` → `open_mesh_device` 반복 20회 무먹통
- 모드 전환(3b+3b/caption-3b/llm-8b/caption-8b) 약 10여 회, 8B 포함, 전부 생존
- `SIGTERM` → worker join → `close_mesh_device` 완료까지 대기하는 정상 종료

**확실히 치명적이라고 확인됨(재확인 불필요, 회피만):**
- 연산 진행 중 `SIGKILL(-9)` — device teardown 스킵 → 보드 dirty
- 6프레임 이상 VLM 캡셔닝 — vision attention 커널이 Tensix 코어를 데드락(FW init 영구 실패, 재부팅 필요)
- PCIe FLR(`/sys/.../reset`) — 링크 자체가 끊겨 버스에서 사라짐(재부팅 필요)
- Ctrl-C 연타 — teardown 도중 인터럽트

**미검증(이번 계획의 실제 타깃):**
- 장시간 연속 대량 요청(수백~천 단위 캡션 연속) — RSS/DRAM 누적 여부
- 동시 요청(다중 클라이언트가 동시에 `/caption`·`/v1/chat` 호출) — 워커 큐 백프레셔가 제대로 도는지
- 빠른 반복 모드 전환(수십~백 회 연속) — 지금까지 10여 회만 검증됨
- 비정상/엣지케이스 페이로드(빈 이미지, 손상된 base64, 초대형 이미지, 빈 messages) — device까지 도달해 예외를 남기는지
- 장시간 유휴 후 첫 요청 — 방치된 KV cache/trace 상태에서 문제 없는지
- 클라이언트 타임아웃/중단 — 워커가 요청 중간에 버려진 job으로 다음 요청에 영향받는지

## 2. 상시 모니터링 (전 티어 공통, 테스트 시작 전 기동)

모든 티어 동안 계속 돌려서 **죽는 순간과 직전 상태를 놓치지 않는다**:

```bash
# A. health 폴링 (2초 간격) — ready flip, mode 불일치, 응답 지연 포착
while true; do
  t=$(date +%s.%N)
  r=$(curl -s -m 5 -w '\n%{http_code}' http://localhost:8100/health)
  echo "[$t] $r"
  sleep 2
done | tee /tmp/stability_health.log

# B. 서버 프로세스 자원 (RSS 누적, 스레드 수)
while true; do
  ps -o pid,etime,rss,vsz,nlwp -p $(pgrep -f "[t]t_infer_server.py") 2>/dev/null || echo "PROCESS GONE"
  sleep 5
done | tee /tmp/stability_rss.log

# C. 서버 stdout 로그 실시간 (에러 패턴)
tail -f /tmp/ttserver457.log | grep -iE --line-buffered \
  "Traceback|failed to initialize FW|Timeout.*physical|out of memory|OOM|Error|Exception"
```

C는 Monitor 도구로 상주시켜, 매칭되는 순간 바로 알림받는 편이 낫다(폴링 대신).

## 3. 테스트 티어 (순서대로, 각 티어 후 go/no-go)

각 티어는 **이전 티어가 완전히 통과해야** 진행. 실패 시 그 티어에서 멈추고 서버 로그·모니터링 로그로 원인 분석 → 다음 티어로 넘어가지 않음.

### T1 — 베이스라인 (검증용, ~5분)
단일 클라이언트, 순차 요청 50회(`/caption` 25 + `/v1/chat` 25, 3b+3b 모드). 목적: 나머지 티어의 대조군.
- **통과 기준**: 50/50 성공, RSS 변동 없음, health 계속 ready

### T2 — 장시간 연속 볼륨 (~2-3시간)
`/caption` 연속 500~1000회(samsung_dataset 전체 or 반복). 목적: RSS/DRAM 누적, program cache 무한 성장 여부.
- **관찰 지표**: 100건마다 RSS 기록 — 선형 증가하면 누수. `mesh_device.num_program_cache_entries()`도 같이 찍을 것(서버에 디버그 엔드포인트 임시 추가 필요할 수 있음).
- **통과 기준**: RSS 안정화(초기 몇십 건 후 플래토), 요청 실패율 0%

### T3 — 동시 요청 (동시성 버그 타깃)
클라이언트 3~5개가 동시에 `/caption`+`/v1/chat` 혼합 요청(각자 순차, 서로 겹치게). 목적: 단일 워커 큐가 요청을 직렬화만 하는지, 아니면 상태 레이스가 있는지(`_state` 딕셔너리 동시 접근, FastAPI가 스레드풀로 핸들러를 돌리는 점 고려).
- **통과 기준**: 모든 요청이 정확한 응답(뒤섞이지 않음), 서버 생존, 큐 대기시간이 예측 가능(선형 증가, 폭발 없음)

### T4 — 빠른 반복 모드 전환 (회수 경로 반복 스트레스)
`/mode`를 20~50회 빠르게 왕복(3b+3b ↔ caption-8b, 회수 비용이 가장 큰 조합). 목적: close+reopen을 10여 회보다 훨씬 많이 반복해도 안정적인지 — 지금까지의 검증 횟수를 뛰어넘는 지점에서 문제가 생기는지 확인.
- **통과 기준**: 전부 성공, 매 전환 후 health ready, 마지막 전환 후 device 자원(RSS/DRAM) 초기 로드 시점과 비슷한 수준으로 복귀

### T5 — 엣지케이스 페이로드
| 케이스 | 기대 동작 |
|---|---|
| `images: []` | 400 (이미 코드에 있음) |
| 손상된 base64 | 500이든 뭐든 **서버가 죽지 않고** 에러 응답 |
| 거대 이미지(예: 20MB) | 처리되거나 명확히 거부, device 오염 없음 |
| `messages: []` | 빈 프롬프트로도 device까지 안 깨지고 처리/에러 |
| 클라이언트가 응답 전 소켓 끊음(curl --max-time 1로 강제 타임아웃) | 워커가 진행 중이던 job을 끝까지 마치고, 다음 요청에 영향 없음 |
- **통과 기준**: 어떤 케이스도 서버 프로세스를 죽이거나 device를 dirty하게 만들지 않음(직후 T1 재실행으로 확인)

### T6 — 장시간 유휴 후 재사용
서버를 30분~1시간 유휴 상태로 두고(아무 요청 없음) 첫 요청. 목적: 방치된 KV cache/trace 상태 문제.
- **통과 기준**: 유휴 직전과 동일한 지연시간·정확도

## 4. 각 티어 실패 시 절차

1. 모니터링 로그(A/B/C) 즉시 백업 — 티어·시각 기록
2. 서버 생존 확인: `curl /health` — 응답하면 **얕은 실패**(요청 단위), 무응답이면 **깊은 실패**(worker/device)
3. 깊은 실패면: `ps`로 서버 프로세스 확인 → 있으면 워커 스레드 hang(디바이스 op 안에 갇힘, 강제 종료는 사용자 승인 필요) → 없으면 크래시(로그의 마지막 traceback이 원인)
4. 보드 자체 확인: `python3 -m ttnn.examples.usage.run_op_on_device` (서버 무관 최소 테스트)
5. FW init 실패면 → `sudo rmmod bos && sudo modprobe bos` → 안 되면 재부팅(NPU 먼저)
6. **`SIGKILL`이나 FLR은 사용자 승인 없이 쓰지 않음** (이번 세션 반복 확인된 규칙)

## 5. 실행 순서 제안

1. 모니터링 A/B/C 먼저 기동 (Monitor 도구로 C를 상주)
2. T1 → T2 → T3 → T4 → T5 → T6 순서, 티어 사이 결과 보고 후 다음 진행 승인받기
3. T2(장시간)가 가장 오래 걸림(2-3시간) — 백그라운드로 돌리고 다른 티어와 시간 순서 조정 가능(T2를 마지막에 돌리며 그동안 T3~T6 먼저 끝내는 것도 방법)

## 6. 아직 결정 안 된 것

- T2/T3의 정확한 규모(요청 수, 동시 클라이언트 수)는 사용자 승인 시 조정
- 디버그용 `program_cache_entries` 노출 엔드포인트를 임시로 서버에 추가할지(T2 관찰력 향상 vs 코드 변경 최소화 원칙 사이 트레이드오프)
- T5의 "거대 이미지" 실제 크기와, curl 타임아웃 시뮬레이션의 정확한 구현 방법
